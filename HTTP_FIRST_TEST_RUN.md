# Запуск и проверка HTTP-first на Windows

Выполняйте команды из корня проекта. Используйте один и тот же Python для всех процессов. Если работаете в виртуальном окружении, активируйте его в каждом терминале.

## Подготовка

В текущем `.env` уже включены `TIKTOK_NETWORK_FIRST=True`, `TIKTOK_NETWORK_IMPL_READY=True`, `PARALLEL_COMMENTING_DOM_FIRST=False` и блокировка `BLOCK_IMAGES`, `BLOCK_MEDIA`, `BLOCK_FONTS`. `USE_BAS` должен оставаться `False`. `DEMO_MODE=0` означает реальный режим со списаниями.

Публикация через HTTP-first использует `window.fetch` внутри Chromium: браузер выполняет JS страницы и хранит cookies. Для скрытых окон установите в `.env` `PLAYWRIGHT_HEADLESS=True`; при `False` окна видны и их можно использовать для отладки. Это браузерный HTTP-транспорт; запуск Chromium сам по себе не означает публикацию через DOM.

При первом запуске на другом компьютере:

```powershell
python -m pip install -r requirements.txt
python -m patchright install chromium
```

Браузер использует Patchright, поэтому устанавливать Chromium нужно именно этой командой. На проверенном компьютере браузер уже установлен, Redis отвечает, подключение к БД работает, `pip check` проходит.

Не создавайте новую БД поверх существующей и не переимпортируйте весь пул ради теста: нормализация применяется при чтении cookies. Для первого заказа достаточно небольшой проверенной группы аккаунтов. В текущем тестовом режиме прокси не используются.

## Запуск

Для текущего теста через домашний интернет в `.env` установлено `USE_PROXY=False`. Перезапустите backend, бота и executor после изменения настройки: уже работающие процессы её не перечитывают. Сохранённые прокси аккаунтов и персональный прокси пользователя в этом режиме игнорируются, назначения в БД сохраняются. Для возврата к обычному режиму установите `USE_PROXY=True` и снова перезапустите процессы. Системный VPN эта настройка не отключает.

Redis должен быть запущен. Перед перезапуском дождитесь завершения текущих заказов и остановите старые процессы через Ctrl+C в их терминалах. Не запускайте два executor или два экземпляра одного Telegram-бота.

Откройте три PowerShell-терминала в корне проекта:

1. Backend:

   ```powershell
   python run_server.py
   ```

2. Telegram-бот:

   ```powershell
   python -m bot.app
   ```

3. Исполнитель:

   ```powershell
   python -m executor.executor
   ```

Если нужен мониторинг блогеров, запустите четвёртый процесс:

```powershell
python -m services.video_monitor_worker
```

Проверка компонентов:

```powershell
curl.exe -s http://127.0.0.1:8000/health
```

В `checks` для `database`, `redis`, `executor` должен быть `status: ok`. Без отдельного video monitor общий `/health` может вернуть HTTP 503: смотрите статусы отдельных компонентов. Если `executor` не `ok`, заказ пока не создавайте.

## Один реальный заказ

1. Перед заказом отметьте начало захвата логов:

   ```powershell
   python scripts/export_executor_logs.py --mark-start
   ```

2. Выберите свой доступный ролик или фото с разрешёнными комментариями и существующим родительским комментарием. Запишите его ID, текст и автора.
3. Сначала создайте минимальный заказ «только ответы»: один ответ под этим родителем, количество — один. Если интерфейс позволяет указать ID, используйте его: это отдельно проверит HTTP-публикацию без поиска по тексту. Не включайте лайки в первый тест.
4. Проверьте превью и создайте ровно один заказ с одним URL. Сверяйте количество публикаций с планом заказа. Старый остановленный заказ автоматически не перезапускайте: часть ответов уже могла быть опубликована.
5. Следите за исполнителем:

   ```powershell
   Get-Content .\logs\executor.log -Tail 100 -Wait
   ```

6. После завершения откройте ролик в отдельной сессии/другом аккаунте. Проверьте видимость основных комментариев и то, что ответы находятся под нужными родителями. Сам по себе ответ API с ID не доказывает публичную видимость.
7. Экспортируйте лог этого запуска:

   ```powershell
   python scripts/export_executor_logs.py --zip
   ```

   Сохраните ID заказа и ZIP, путь к которому выведет команда. Архив пригодится, если публикация или проверка видимости не прошла.

## Проверка поиска и трёх режимов

После первого успешного ответа повторите небольшой тест с поиском родителя по тексту и автору. В логах должен появиться `[PARENT_HTTP] available=True` и найденный ID; строки открытия/скроллинга списка комментариев в этой ветке появляться не должны. Затем проверяйте три режима последовательно:

1. **Main-only:** три разных главных текста, без ответов. Если все требуемые публикации получили числовые ID через HTTP и `network_confirmed=True`, итог должен быть `success` без запуска DOM-observer.
2. **Full Hybrid:** главные тексты и ответы. Успешный HTTP-ответ подтверждает существование родителя для итоговой классификации главных комментариев. Полный `success` требует выполнения всех запланированных главных публикаций и ответов; одного успешного ответа недостаточно для завершения всего заказа.
3. **Replies-only:** ответ под существующим комментарием. Укажите его ID либо текст и автора. Новые главные комментарии для этого режима не нужны. Родитель, найденный через `/api/comment/list/`, учитывается найденным даже при последующей ошибке отправки ответа; сама ошибка не считается успешной публикацией.

Автор основного комментария берётся со страницы, а при его отсутствии — из `comment.user.unique_id` ответа публикации, затем из `nickname`. Это значение используется при выборе цели автолайков. Подтверждение API не гарантирует видимость для других пользователей: её проверяйте отдельной сессией после каждого заказа.

## Признаки успешной проверки

- Публикации получают реальные числовые `comment_id`; ответы подтверждают нужный `parent_comment_id`.
- В результате/логах публикации используются методы `http_user_schema`; транспорт HTTP-клиента — `window.fetch`. Для ответов режим проверки обозначается `http_parent_id`, сохраняется ID ответа. В HTTP-first недоступная сессия, отказ API или капча останавливают попытку аккаунта; исполнитель может выбрать следующий аккаунт в пределах лимитов. Главные комментарии и ответы не переключаются на DOM-кликер. Явно выбранный DOM-first режим продолжает работать отдельно.
- Перед HTTP-прогревом ожидается событие `load` (до 8 секунд, затем `domcontentloaded`), затем признаки готовности SDK/перехватчика в основном JS-контексте (до 8 секунд). Эти признаки помогают выбрать момент отправки, но сами по себе не доказывают корректность подписи.
- Строка `HTTP_RESPONSE` показывает транспорт, номер попытки, HTTP-статус, длину тела и наличие параметров безопасности в URL ответа. Значения токенов не выводятся. Отсутствие этих параметров в URL само по себе не доказывает причину отказа.
- Строка `[COMMENT_LIST_HTTP]` объясняет отказ поиска: `empty_body`, `http_status`, `api_status`, `invalid_json`, `missing_comments`, `timeout` или тип исключения. Ошибка API-поиска имеет режим `http_comment_list`. `reply_http_stopped` сохраняет причину отказа подготовки, включая капчу. Успешная паспортная проверка cookies не гарантирует доступ к API комментариев.
- При первом пустом ответе HTTP 200 на POST публикации разрешён один повтор через 2 секунды, если политика повторов включена. Повторный пустой ответ останавливает серию аккаунта без переключения следующих вариантов в DOM; такой результат не закрывает слот основной публикации и не засчитывает ответ как отправленный.
- Успешный тест получает непустой JSON и ID публикации. Если сервер продолжает отдавать `body_len=0`, это остаётся отказом HTTP; такой аккаунт не должен запускать DOM-публикацию. Отсутствие глобального signer само по себе не запрещает запрос, а неопределённый результат отправки защищён от немедленного дублирования.
- При известных подтверждённых ID HTTP-ответы не требуют предварительного DOM-поиска родителя. Пропущенный observer не выдаётся за подтверждение публичной видимости.
- Для ответа по тексту/фразе сначала выполняется `/api/comment/list/` с профилем текущей страницы и свежими cookies: по умолчанию до десяти страниц по 50 комментариев; явно заданный `max_pages` допускает до двадцати страниц. Автор проверяется, если задан. Найденный числовой `cid` разделяется между потоками заказа. Недоступный API завершает попытку с `parent_api_unavailable:<причина>`; это не доказательство отсутствия родителя. Корректный JSON без совпадения, включая `comments: null`, также не запускает DOM-скроллинг. Лимит страниц не гарантирует просмотр всех комментариев большого ролика.
- Перед публикацией в HTTP-режиме нет отдельного DOM-обогащения через `/foryou`: cookies получаются на целевой странице во время HTTP-прогрева. Повторно занятые и уже выполненные цели отсеиваются до открытия очередного браузера.
- Пустой ответ на публикацию reply не считается успехом даже при появлении текста в этой же вкладке: локальная отрисовка React не подтверждает сохранение на сервере. Вариант остаётся для повторной попытки с другим аккаунтом.
- При загрузке cookies из БД исключаются `_waftokenid`, `csrf_session_id`, `x-web-secsdk-uid`, `perf_feed_cache`, `tt_session_tlb_tag`, `tt_csrf_token`, а также `msToken` с синтетическим сроком не менее `2000000000`. Реальный срок и последняя запись вращаемого токена приоритетнее экспортного срока до 2038 года. После ожидания готовности перехватчика выполняется GET списка комментариев для прогрева JS и обновления cookies; при сохранении прогретого контекста очистка отключена, поэтому свежие cookies не теряются.
- Перед каждой попыткой HTTP, включая повтор после пустого ответа и следующий вариант текста, перечитываются cookies браузерного контекста и заново собираются URL, заголовки и тело запроса. Свежие `tt_csrf_token` и `WebIdLastTime` имеют приоритет над переданными значениями. В исходный URL браузерных `/api/comment/publish/` и `/api/comment/list/` `msToken` вручную не вставляется: его добавляет перехватчик страницы.
- В `window.fetch` передаются только `accept`, `accept-language`, `tt-csrf-token` и `content-type`. Служебные `x-secsdk-*` не задаются вызывающим кодом; POST имеет `application/x-www-form-urlencoded; charset=UTF-8`. Cookie `tt_csrf_token` не подставляется в `x-secsdk-csrf-token`. Штатный SDK может выполнить служебный HEAD и добавить свой CSRF-токен к POST.
- В режиме без прокси короткая ссылка разрешается заранее; канонический адрес, полученный браузером, передаётся следующим попыткам. Распознанные сбои сессии, капча и ошибки перехода до отправки не тратят рабочую попытку публикации; число замен аккаунтов отдельно ограничено `MAX_RETRY_ACCOUNTS`.
- В БД сохраняются полученные при прогреве `ttwid` / `tt_csrf_token`; cookies и токены не нужно вручную копировать в логи.
- Итоговые количества совпадают с планом заказа, а отдельная сессия действительно видит комментарии и ответы.

## Диагностика живого API без публикации

Добавлен `scripts/probe_comment_api.py`. Он читает cookies выбранного аккаунта, открывает страницу и выполняет GET списка комментариев. В отдельном браузере скрипта запросы `/api/comment/publish/` заблокированы; cookies аккаунта в БД не обновляются. Вывод содержит статусы и количества без значений токенов и текстов комментариев.

Пример: замените `2445`, адрес и ID родителя своими значениями; URL оставьте в кавычках.

```powershell
python -X utf8 scripts/probe_comment_api.py --account-id 2445 --url "https://www.tiktok.com/@ACCOUNT/photo/VIDEO_ID" --compare-minimal --target-parent-id "COMMENT_ID"
```

`available=true` и `target_parent_in_page=true` означают, что API ответил и родитель найден на первой странице. Диагностика использует отдельный контекст напрямую через текущий интернет и сравнивает минимальный и полный набор параметров; это не точная копия всех настроек браузерного пула. На проверке двух аккаунтов один вернул 49 комментариев, второй — пустое тело при обоих наборах параметров. По одному HTTP 200 нельзя считать сессию готовой к публикации. Подробный разбор: `HTTP_FIRST_AUDIT_1213.md`.
