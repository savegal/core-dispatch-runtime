# Проверка фактической готовности HTTP-first

Дата: 16 октября 2026 года. Проверены рабочие процессы, реальные заказы в БД, полный лог executor и живой сервис через штатный BrowserPool. Новые комментарии и ответы не публиковались.

## Вывод

**До веб-публикации софт дошёл. До подтверждённой стабильной публикации с видимостью для другого аккаунта — пока нет.**

Главные комментарии уже получали реальные числовые ID через `window.fetch`. Но пустые ответы остаются, а проверка другим аккаунтом не подтвердила видимость этих публикаций. Успешный ответ API и публичная видимость должны оцениваться отдельно.

Наличие `X-Bogus` и `X-Gnarly` встречается и у пустых ответов. Следовательно, одно наличие параметров безопасности не доказывает, что сервер примет запрос.

## Живой штатный транспорт

Добавлена диагностика `scripts/verify_http_pipeline.py`. Она использует настоящий BrowserPool с текущими настройками, настоящие cookies, прогрев, JS страницы и PlaywrightHttpClient. Прокси отключены; режим окна соответствует текущему `PLAYWRIGHT_HEADLESS=False`. DOM-публикаторы не вызываются.

Проверены аккаунты 2445 и 2507 на том же фото. На обоих:

- прогрев успешен, признаки готовности SDK присутствуют;
- GET комментариев возвращает валидный JSON;
- в браузерном контексте есть `sessionid`, `sid_tt`, `sessionid_ss`, `ttwid`, `tt_csrf_token`, `msToken`;
- POST главного комментария и ответа формируется через `window.fetch`;
- реальный перехватчик страницы добавляет `X-Bogus`, `X-Gnarly` и `msToken`;
- текст формы, поля ответа и ID родителя сохраняются;
- браузер отправляет сессионные cookies;
- после служебного HEAD сервер отвечает HTTP 200 с заголовком `x-ware-csrf-token`, а POST содержит CSRF-заголовок, отличный от `DOWNGRADE`.

**Все запросы публикации в этой диагностике перехвачены и получили локальный ответ без ID. Ни один из четырёх POST не отправлялся в TikTok.** Служебный HEAD разрешён: его блокировка сама мешала проверке CSRF. Равенство CSRF-заголовка и cookie `tt_csrf_token` не подтверждено; при работающем перехватчике это само по себе не доказывает ошибку, поскольку наблюдался отдельный HEAD-обмен.

Сохранённые cookies обоих аккаунтов в БД после диагностики не изменились.

Результат: `output/playwright/production-http-verification-final.jsonl`. В нём только статусы, ID и признаки наличия данных; значений токенов и текстов комментариев нет.

Но эта проверка **не подтверждает видимость для другого аккаунта**, которую нельзя выводить из полученного при публикации ID. Результат публикатора также неполный из-за отказа пагинации.

## Работающий executor

В момент проверки:

- executor PID 12672 запущен 15 октября в 23:04:23;
- последние изменения рабочих модулей сохранены 16 октября после 04:07;
- следовательно, текущий процесс не подтверждает загрузку последних исправлений; нужен перезапуск;
- новых реальных заказов после 1216 в БД нет, активных и ожидающих заказов не обнаружено;
- свежие строки успешных HTTP-вызовов после 04:00 относятся к тестам, записанным в общий лог; они исключены из оценки реальных публикаций;
- database, redis и executor отвечают `ok`; общий `/health` — 503 из-за `video_monitor`, который не требуется для ручного заказа.

## Что осталось подтвердить

1. Перезапустить executor с последним кодом.
2. Выполнить один разрешённый тест на своём видео с заранее известным текстом и родительским ID, если это ответ.
3. Получить реальный ID через HTTP и проверить его видимость другим аккаунтом. При пустом ответе или отсутствии видимости не считать цель проверки достигнутой.
4. После этого проверить отдельно Main-only, Full Hybrid и Replies-only, включая повторные варианты на одном аккаунте.

Прежние 827 успешных тестов и 20 браузерных интеграционных проверок подтверждают поведение кода при заданных ответах. Они не заменяют эти проверки живого сервиса.

Существующие рабочие модули при этой проверке не менялись. Добавлены диагностический скрипт `scripts/verify_http_pipeline.py` и этот отчёт. Процессы не перезапускались, заказы и аккаунты в БД не изменялись.
