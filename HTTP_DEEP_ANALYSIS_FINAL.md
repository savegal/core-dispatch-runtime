## 🔍 ДЕТАЛЬНЫЙ АНАЛИЗ КОМПОНЕНТОВ

### 1. АРХИТЕКТУРА HTTP ЗАПРОСОВ

#### 1.1. Компоненты

**Основные файлы:**
- `executor/engagement_engine.py` - основная логика
- `executor/http/playwright_http_client.py` - HTTP клиент
- `executor/http/request_profile.py` - профили запросов
- `executor/http/retry_policy.py` - политика retry

**Flow выполнения:**
```
1. Создание заказа (API) → HOLD баланса
2. Executor получает задачу → status="in_progress"
3. Для каждого video_url:
   a) HYBRID FULL: Main comment (DOM) → Verify (DOM) → Replies (HTTP) → Likes (HTTP)
   b) ENGAGEMENT ONLY: Find comment → Replies (HTTP) → Likes (HTTP)
4. Сохранение url_results в унифицированном формате
5. Финализация → Refund для failed videos
```

### 2. НАЙДЕННЫЕ ОШИБКИ И ИСПРАВЛЕНИЯ

#### ✅ ИСПРАВЛЕНО: Ошибка 1 - DOM fallback внутри retry loop

**Проблема:**
- DOM fallback выполнялся **внутри** retry loop для replies
- При каждой неудачной попытке HTTP → DOM fallback → новая попытка HTTP → DOM fallback
- **Избыточные fallback'и** замедляют выполнение

**Исправление:**
- DOM fallback вынесен **после** всех retry попыток HTTP
- Выполняется один раз с новым аккаунтом
- Код: строка 691-725 → после цикла retry

**Результат:**
- ✅ Нет избыточных DOM fallback'ов
- ✅ Логика стала проще и понятнее
- ✅ Экономия ресурсов

---

#### ⚠️ ЧАСТИЧНО ИСПРАВЛЕНО: Ошибка 2 - Нет retry для likes

**Проблема:**
- Likes не имеют retry с разными аккаунтами (в отличие от replies)
- Если HTTP упал с retryable ошибкой - лайк сразу проваливается

**Исправление:**
- Добавлен DOM fallback для **всех** ошибок (не только FORBIDDEN/CAPTCHA)
- Likes используют разные аккаунты (создаются заранее)
- Но: нет retry с новым аккаунтом если HTTP упал (используется тот же)

**Результат:**
- ✅ DOM fallback для всех ошибок (справедливость)
- ⚠️ Нет retry с новым аккаунтом (можно улучшить позже)

---

#### ✅ ИСПРАВЛЕНО: Ошибка 3 - Не исключаются использованные аккаунты

**Проблема:**
- При retry для replies `exclude_ids=None` → может быть выбран тот же аккаунт
- Бесполезно: если аккаунт упал с 403, повторная попытка тоже упадёт

**Исправление:**
- Добавлен список `used_account_ids` (строка 584)
- Аккаунты исключаются в retry loop (строка 588)
- Аккаунт добавляется после использования (строка 594)

**Результат:**
- ✅ Разные аккаунты в retry
- ✅ Нет повторного использования проблемных аккаунтов

---

#### ✅ ИСПРАВЛЕНО: Ошибка 4 - Нет задержек между лайками

**Проблема:**
- Все 15 лайков выполняются почти одновременно
- Риск rate limit на прокси/IP

**Исправление:**
- Добавлена случайная задержка 0.5-2.0 сек между лайками (после строки 1000)
- Задержка не применяется после последнего лайка

**Результат:**
- ✅ Снижен риск rate limit
- ✅ Более "человечное" поведение

---

#### ✅ ИСПРАВЛЕНО: Ошибка 5 - DOM fallback только для FORBIDDEN/CAPTCHA

**Проблема:**
- DOM fallback для likes только при фатальных ошибках
- Несправедливо: replies имеют fallback для всех ошибок

**Исправление:**
- DOM fallback добавлен для **всех** ошибок (строка 965-993)
- Выполняется после каждого HTTP запроса, если он упал

**Результат:**
- ✅ Справедливость: likes и replies имеют одинаковую логику fallback
- ✅ Больше успешных лайков через DOM

---

#### ✅ ИСПРАВЛЕНО: Ошибка 6 - Нет проверки comment_id

**Проблема:**
- `comment_id` может быть пустым, но лайки всё равно пытаются выполниться
- Тратятся ресурсы на создание contexts и warmup

**Исправление:**
- Добавлена проверка в начале функции (строка 773-783)
- Если `comment_id` пустой - возвращаются ошибки сразу

**Результат:**
- ✅ Раннее обнаружение ошибок
- ✅ Экономия ресурсов

---

#### ✅ ИСПРАВЛЕНО: Ошибка 7 - Нет проверки успешности warmup

**Проблема:**
- Если warmup упал, аккаунт остаётся в `accounts_to_use`, но нет context
- При использовании - ошибка "Context not available"

**Исправление:**
- Аккаунт добавляется в `accounts_to_use` только если warmup успешен (строка 820)
- Если warmup упал - пробуется следующий аккаунт (строка 831)
- Context закрывается при ошибке (строка 824-830)

**Результат:**
- ✅ Нет ошибок "Context not available"
- ✅ Только успешные аккаунты используются

---

#### ⚠️ ЧАСТИЧНО РЕШЕНО: Ошибка 8 - Cooldown в текущем цикле

**Проблема:**
- Cooldown применяется, но аккаунт может быть выбран в том же цикле (до commit)

**Решение:**
- Cooldown проверяется в `get_free_account_for_reply()` (уже исправлено ранее)
- `used_account_ids` предотвращает повторное использование в том же цикле

**Результат:**
- ✅ Аккаунт не будет выбран повторно в том же цикле
- ⚠️ Теоретически возможен race condition между commit и следующим запросом (редко)

## 📊 АНАЛИЗ ЛОГИКИ ВЫПОЛНЕНИЯ

### 3.1. Replies (execute_replies_http)

**Текущая логика (после исправлений):**

```
Для каждого reply:
  1. used_account_ids = []
  2. Retry loop (3 попытки):
     a) Получить аккаунт (исключая used_account_ids)
     b) Добавить в used_account_ids
     c) Создать context/page
     d) Warmup → валидация профиля
     e) Если профиль невалиден → continue (следующий аккаунт)
     f) HTTP запрос через PlaywrightHttpClient
     g) Если success → break (успех)
     h) Если 429 → cooldown аккаунта, continue (следующий аккаунт)
     i) Если 403/капча → continue (следующий аккаунт)
     j) Если другая ошибка → continue (следующий аккаунт)
  3. Если HTTP не сработал → DOM fallback (один раз, с новым аккаунтом)
  4. Сохранить результат
```

**✅ Сильные стороны:**
- Разные аккаунты в retry
- DOM fallback после всех попыток (не избыточно)
- Cooldown применяется правильно

**⚠️ Потенциальные улучшения:**
- Можно добавить retry с новым аккаунтом для DOM fallback (если первый упал)

---

### 3.2. Likes (execute_likes_http)

**Текущая логика (после исправлений):**

```
1. Проверка comment_id (ранняя)
2. Сбор аккаунтов с успешным warmup:
   - Пробуем до likes_count * 2 аккаунтов
   - Если warmup упал - аккаунт не добавляется
   - Создаём contexts для всех успешных аккаунтов
3. Для каждого лайка:
   a) Использовать заранее созданный context
   b) Если профиль невалиден → DOM fallback сразу
   c) HTTP запрос
   d) Если success → OK
   e) Если упал → DOM fallback (для всех ошибок)
   f) Задержка 0.5-2.0 сек (кроме последнего)
4. Закрытие всех contexts разом
```

**✅ Сильные стороны:**
- Оптимизация ресурсов (один context на аккаунт)
- Задержки между лайками
- DOM fallback для всех ошибок
- Ранняя проверка comment_id

**⚠️ Потенциальные улучшения:**
- Можно добавить retry с новым аккаунтом если HTTP упал (сейчас используется тот же)

**Проблема:** Нет проверки, что страница действительно загрузилась.

**Решение:**
```python
# После page.goto()
if "/video/" not in page.url:
    logger.warning("Page redirect detected, retrying...")
    continue

# Проверка элемента видео
try:
    video_element = await page.query_selector("video")
    if not video_element:
        logger.warning("Video element not found, retrying...")
        continue
except:
    pass
```

**Приоритет:** Средний (можно добавить позже)
