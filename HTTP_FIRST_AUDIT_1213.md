# Разбор HTTP-first: заказ 1213

Проверка кода и логов выполнена 16 октября 2026 года. Исходный лог — вложение `e25d4dea-1f72-4e12-9113-a5df981752b9`, интервал заказа: 15 октября, 22:31:41–22:41:13. Это заказ только на ответы, остановленный пользователем.

## Что действительно произошло

Публикация действительно переходила на DOM. Открытые окна сами по себе этого не доказывают, но в логе есть прямые вызовы открытия списка, DOM-поиска и DOM-публикации.

| Наблюдение | Количество |
| --- | ---: |
| Создания страниц/начальные переходы | 93 |
| Неудачный поиск API: `available=False scanned=0` | 10 |
| Открытия списка комментариев через DOM | 14 |
| Попытки прямого HTTP-ответа | 4 |
| Успешные HTTP-ответы | 2 |
| Строки HTTP_RESPONSE с учётом повторов | 6 |
| Результаты DOM-публикации ответа | 8 |
| Из них пустые неуспешные ответы | 7 |
| Из них таймаут, зачтённый по локальному DOM | 1 |
| Отказы прогрева из-за капчи | 5 |

К остановке учитывались 3 из 5 ответов: два с подтверждением API и один по локальному DOM. Полного завершения заказа этот лог не подтверждает.

Причинная цепочка: поиск `/api/comment/list/` возвращал недоступный API без подробной причины → код разрешал запасной DOM-поиск → открывал список, прокручивал его и пытался отправлять ответ через интерфейс. Аналогичный переход оставался после неготовой HTTP-сессии, в том числе после капчи. Позже найденный родительский ID попадал в общий кеш, и другие аккаунты уже могли отвечать прямо через HTTP.

Ещё одна ошибка отчётности: HTTP-ответ обозначался как `full_flow_dom_parent`, а его ID терялся при преобразовании результата. Исправлены и реальное переключение транспорта, и неправильная метка.

## Проверка живого GET API

Выполнены только запросы чтения к тому же фото. Публикации были заблокированы маршрутизацией отдельного диагностического контекста; аккаунты в БД не изменялись.

| Аккаунт | Минимальные параметры GET | Полный профиль GET |
| --- | --- | --- |
| 1940 | HTTP 200, пустое тело | HTTP 200, пустое тело |
| 2445 | HTTP 200, 49 комментариев | HTTP 200, 49 комментариев; нужный родитель найден |

Это подтверждает, что прямой GET работает на живом сервисе для части сессий. Оно также показывает, что добавление параметров не устраняет пустые ответы у всех аккаунтов. Серверную причину отказа аккаунта 1940 по этим данным установить нельзя. Паспортная проверка подлинности сессии и допуск API комментариев — разные проверки.

Диагностика запускается в отдельном Patchright-контексте напрямую через текущий интернет; она не воспроизводит все настройки штатного браузерного пула. Поэтому её результат не равен проверке реальной публикации заказа.

## Исправления

1. В HTTP-режиме ошибки подготовки, API-поиска и отправки ответа завершают попытку аккаунта. Открытие списка, скроллинг и DOM-публикация не включаются. Общий старый обработчик также прекращает HTTP-попытку при ошибке прогрева, временном запрете HTTP и отказе до отправки. Его выбор транспорта теперь учитывает общую настройку режима: аккаунт с рекомендацией только DOM не обходит HTTP-режим и пропускается до создания браузера.
2. Поиск родителя использует профиль текущей страницы, язык, таймзону и свежие cookies. Извлечение профиля и GET выполняются в основном JS-контексте, где работает перехватчик страницы. Чужие готовые подписи не копируются.
3. Логи поиска различают пустое тело, HTTP/API-отказ, некорректный JSON, отсутствие списка, таймаут и исключение. Причина капчи сохраняется при отказе подготовки вместо безликого `http_session_not_ready`.
4. HTTP-ветки главного комментария и ответа не запускают предварительное DOM-обогащение через `/foryou`. Прогрев и сохранение cookies выполняются на целевой странице.
5. После недавней успешной паспортной проверки HTTP-ветка проверяет целевой URL, фактические cookies контекста, капчу и видимый logout, не ожидая DOM-маркеров профиля. Это не обходит видимую капчу или форму входа.
6. Уже выполненные и временно занятые цели ответов отсеиваются до создания браузера. Существующие блокировки защищают от дублирования между потоками.
7. В результате HTTP-ответа сохраняется ID и режим `http_parent_id`; публичная DOM-видимость ему не приписывается. Ошибка API-поиска обозначается `http_comment_list`, также без ложной DOM-метки. Найденный через API родитель учитывается независимо от успеха POST.

## Проверка и ограничения

Регрессионные тесты проверяют три режима заказа, cookies, повторные запросы, подписи, поиск/пагинацию, блокировки дубликатов и учёт результатов. Браузерные интеграционные тесты работают в настоящем Chromium с локальными ответами. В том числе они проходят путь «GET родителя → POST ответа», а также пустой GET и капчу, запрещая вызовы DOM-поиска и DOM-публикации.

Общий прогон: **827 passed**, 261,97 секунды, в том числе **20 браузерных интеграционных тестов**. Проверки границы режимов: **168 passed**. После уточнения метаданных HTTP-поиска повторно прошли **96 проверок** готовности, навигации и трёх режимов заказа. Эти количества перекрываются, складывать их не следует. Зависимости: `pip check` — без ошибок.

При проверке работающего приложения БД, Redis и executor вернули `status: ok`. Общий `/health` — HTTP 503 из-за `video_monitor: error`; отдельный монитор не нужен для ручного заказа.

Настоящий POST в TikTok в ходе этой проверки не выполнялся. Пустой серверный ответ остаётся ошибкой, а подтверждение API с ID не доказывает публичную видимость комментария для другого пользователя.

Порядок перезапуска, минимального реального заказа без прокси и сбора логов: `HTTP_FIRST_TEST_RUN.md`. Уже запущенный executor необходимо перезапустить, иначе он продолжит исполнять старый код.
