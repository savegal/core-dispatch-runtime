# Черновик аудита TikTok main-комментариев — 2026-08-20

Статус на 2026-08-26: критичные подтверждённые дефекты исправлены; вторичные пункты и идеи не внедрялись.

## Область и способ проверки

Проверял путь публикации главных комментариев: выбор аккаунта → открытие browser/context/page с назначенным proxy → поиск/подготовка главного композера → клик `Post` → перехват `/api/comment/publish/` → локальное подтверждение → учёт main-слота → закрытие страниц/контекстов → барьер и ротация 6×1. Отдельно просмотрел production-журналы, но не выполнял реальную публикацию в TikTok: это потребовало бы внешнего побочного эффекта и рабочих аккаунтов.

Повторная проверка 2026-08-26 охватила активный поиск родительского main-комментария, top-level/reply разграничение, поиск main/reply полей, привязку reply-композера к родителю, поиск кнопок отправки и финальное восстановление отправки. На публичном текущем DOM TikTok без авторизации проверены только read-only элементы; ввод и публикация проверялись по коду, тестам и свежим production-логам.

Актуальные read-only маркеры TikTok, подтверждённые живой проверкой:

- текст top-level комментария: `span[data-e2e="comment-level-1"]`;
- корень строки: `div[class*="DivCommentObjectWrapper"]` / безопасный широкий fallback `[class*="DivCommentObject"]`;
- действие ответа: `p[data-e2e="comment-reply-1"]` и его semantic button;
- username marker: `[data-e2e="comment-username-1"]`, но сейчас это `DIV` с display name, а реальный `uniqueId` находится в ссылке `/@username`;
- видимый `DivCommentListContainer` не всегда скроллится сам; активный скролл-ancestor выше имеет `overflow-y: scroll`. Текущий resolver находит именно ancestor.

Главный принцип исправления: слот можно считать занятым только по сигналу, который появился **после попытки отправки**. Активная кнопка до клика доказывает лишь готовность UI.

| Наблюдение | Новый результат | Логика |
|---|---|---|
| Ответ содержит `comment_id` | confirmed | TikTok вернул идентификатор созданного комментария |
| Точный текст найден в DOM у ожидаемого автора | local-confirmed | Авторская привязка защищает от совпадения с чужим одинаковым текстом |
| Запрос зафиксирован, но ответ пуст/потерян | submitted-unconfirmed | Повтор опасен дублем, поэтому решение оставляется observer-у |
| Композер очистился и связанная кнопка стала disabled | submitted-unconfirmed | Это устойчивый UI-переход после отправки, хотя network-body отсутствует |
| `Post` был enabled только до клика | failed/retry | Это не доказательство отправки |
| API вернул ненулевой `status_code` | failed/retry | Это явный отказ TikTok, а не неоднозначный успех |
| Композер визуально пуст, `Post` остаётся enabled, запроса нет | failed/retry на свежем контексте | Текст остался во внутренней модели редактора; отправки не было |

## Подтверждённые критичные ошибки — исправлено

### C1. Main-слот ложно считался отправленным по одному `Post enabled`

**Симптом.** Любой некритический `PublishResult` с `post_was_enabled_at_click=True` попадал в `published`, даже если request не ушёл или TikTok явно отклонил комментарий. В 6×1 такой элемент закрывал обязательный слот, после чего reply-фаза искала родителя, которого нет.

**Причина.** В `_publish_all_variants_on_account` был общий fallback «если кнопка была активна — считать отправленным ради защиты от дубля». Он перекрывал более точную классификацию из `publish_action`.

**Правка.** Общий fallback удалён. `submitted_unconfirmed` разрешён только для перечисленных неоднозначных причин и при наличии подходящего сетевого/DOM-сигнала. Во всех режимах — обычный DOM, parallel DOM и HTTP-first — пустой/потерянный ответ с реально зафиксированным request сохраняется как unconfirmed: TikTok может создать комментарий без пригодного ответа, а повтор способен создать дубль.

**Почему безопаснее.** Явные отказы и доказанное отсутствие request теперь не расходуют слот. Действительно неоднозначный сетевой submit по-прежнему не повторяется автоматически.

### C2. Main direct-DOM игнорировал ненулевой TikTok `status_code`

**Симптом.** Ответ HTTP 200 с JSON вроде `status_code != 0` и без `comment_id` мог стать `main_direct_*_without_comment_id` либо `*_composer_cleared*`, а затем — `submitted_unconfirmed`. Это превращало явный API-reject в выполненный main.

**Причина.** Reply direct-DOM уже проверял внутренний TikTok status, а main direct-DOM — нет. Отдельно тот же пропуск существовал в ветке, где JS-клик завершился timeout, но сетевой listener успел получить ответ.

**Правка.** В обеих ветках main direct-DOM ненулевой TikTok `status_code` возвращается как `api_error_status_code=...` до любой неоднозначной классификации.

**Почему безопаснее.** HTTP 200 больше не ошибочно трактуется как успех приложения: решение принимается по бизнес-коду TikTok.

### C3. Рассинхронизация «пустой DOM, красный Post» обходила direct fallback

**Симптом.** Видимый текст исчезал, но счётчик/красная кнопка показывали, что текст всё ещё находится во внутреннем состоянии редактора; network request отсутствовал. Обычный путь уже умел заметить этот случай, main direct-DOM — нет.

**Правка.** Общая проверка выполняет два probe с settle-интервалом. Если связанный `Post` стабильно остаётся enabled и request не зафиксирован, результат — `composer_empty_but_post_still_enabled`, `composer_clean_after_submit=False`; серия на текущем браузере останавливается, текст можно безопасно повторить на свежем контексте.

**Почему два probe.** Один снимок сразу после клика может попасть в короткий переход TikTok и дать ложный отказ.

### C4. Main-путь мог читать и даже нажать reply-кнопку

**Симптом.** Document-wide селектор главного `Post` включал общие `comment-post` элементы. При нескольких DOM-узлах первый disabled-клон немедленно завершал поиск, а reply-кнопка могла быть принята за main-кнопку.

**Правка.** Поиск enabled-кнопки и все main click fallbacks теперь начинают с ближайшего контейнера конкретного top-level editor, исключают reply scope и ставят отдельный `data-smart-main-post`. Direct-DOM также отбрасывает reply-scoped raw/target nodes. Без связанного main-композера document-wide fallback доверяет только явным main-маркерам.

**Почему безопаснее.** Exact-text gate теперь связан не только с главным полем, но и с кнопкой того же типа. Если безопасную main-кнопку доказать нельзя, отправка остановится вместо возможной публикации ответа не туда.

### C5. Нормализация могла подтвердить другой emoji-комментарий

**Симптом.** Удаление U+200D превращало ZWJ-family `👨‍👩‍👧` в последовательность `👨👩👧`. Удаление skin-tone делало `👍🏻` и `👍🏿` строгим совпадением. Author-scoped проверка защищает от чужого аккаунта, но не от нескольких вариантов одного автора.

**Правка.** Сохраняются ZWJ и skin-tone modifiers. Визуальные variation selectors VS1–VS16 по-прежнему игнорируются, потому что TikTok может добавлять/убирать их без изменения видимого символа.

**Компромисс.** Если TikTok действительно удалит skin-tone из DOM, локальное подтверждение станет осторожным false-negative, а не опасным false-positive. Для защиты от дублей это предпочтительнее.

### C6. Аккаунт мог продолжить работу через старый proxy после переназначения

**Симптом.** `BrowserPool` кэшировал context только по `account_id`. Если `account.proxy` в БД менялся, существующий context всё равно физически оставался в browser, запущенном со старым proxy/IP.

**Правка.** При каждом повторном получении page сравнивается browser-id текущего назначения с browser-id кэшированного context. Idle context на старом proxy закрывается вместе с неиспользуемым browser/локальным SOCKS lease, после чего создаётся новый. Если в старом context ещё есть занятая page, переключение запрещается явной ошибкой: активную отправку нельзя незаметно оборвать или провести через другой IP.

**Почему критично.** Иначе логика замены/ротации proxy существовала только в БД, а реальный Chromium продолжал работать со старым маршрутом.

### C7. Proxy credentials попадали в runtime-логи

**Симптом.** Несколько путей писали `proxy[:30]`/`proxy[:50]`. В типичном URI начало содержит `user:password@...`. Общий URL sanitizer закрывал credentials только при наличии `scheme://`, но не в распространённом формате `user:pass@host:port`.

**Правка.** Sanitizer теперь разбирает scheme-less proxy как authority и редактирует userinfo. Прямые срезы proxy в TikTok validation, health/geo/assignment/concurrency/replacement, mobile rotation и BAS parsing заменены безопасным представлением.

**Почему критично.** Пароль proxy не должен переживать обычную сетевую ошибку в долговременном executor log.

### C8. Текущий TikTok DOM выдавал display name вместо username автора

**Симптом.** Поиск сначала читал `[data-e2e="comment-username-1"]`. В актуальном DOM это `DIV` с отображаемым именем, например локализованным/emoji-именем, тогда как ожидаемый автор хранится как TikTok `uniqueId`. Реальный комментарий поэтому отбрасывался как `author_mismatch`.

**Правка.** Автор извлекается сначала из явной ссылки `/@username` внутри username marker/строки; display name остаётся только диагностическим fallback. Ссылки внутри узла текста комментария исключены, чтобы упоминание `@expected_user` не считалось автором.

**Почему критично.** Иначе строгий author+text поиск систематически не находил собственные комментарии на текущей разметке.

### C9. Три production-входа сознательно отключали author+text

**Симптом.** Parallel replies, полный reply-flow и engagement-only при наличии `tiktok_username` передавали `require_parent_author_match=False`. Одинаковый текст другого пользователя мог стать родителем ответа.

**Правка.** Для кандидатов с известным автором включён обязательный author+exact-text. Кандидаты без автора в том же batch по-прежнему ищутся только по exact-text. Запрещён скрытый переход строгого single-search к text-only после author miss.

**Почему критично.** Это предотвращает отправку ответа под физически чужой комментарий и ложную отметку ожидаемого родителя как обработанного.

### C10. Username мог браться у автора просматриваемого ролика

**Симптом.** `extract_tiktok_username` первым читал `webapp.user-detail`/`pageProps.userInfo`/`serverCode.user`. Эти stores описывают субъект открытой страницы — профиль или автора видео — и не доказывают личность залогиненного аккаунта.

**Правка.** Оставлены только authenticated app-context paths и явная nav-profile ссылка. Если безопасный username неизвестен, возвращается `None`, и этот конкретный main остаётся в text-only режиме.

**Почему критично.** Неверный author hint хуже отсутствующего: строгий поиск гарантированно пропустит реальный main или привяжется к чужой строке.

### C11. Send-only recovery запускался после изменения reply-черновика

**Симптом.** Свежий лог показывает: exact reply text введён, кнопка осталась disabled, затем `_clear_reply_comment_composer_best_effort` вернул `cleared=false`, но частично изменил contenteditable; следующий send-only recovery немедленно завершился `text_mismatch`.

**Правка.** Если `publish_reply_hybrid` действительно имеет финальный recovery deadline и причина recoverable, точный черновик сохраняется до rebind/send-only. В прямом вызове без recovery cleanup остаётся прежним.

**Почему безопасно.** До этого этапа клика не было, поэтому сохранение текста не меняет правило «введено + нажато = вероятно отправлено» и не создаёт повторную отправку.

### C12. Legacy DOM-verifier сначала находил текст, а автора проверял постфактум

**Симптом.** При двух одинаковых текстах verifier мог получить первую чужую строку, отклонить её по автору и не продолжить поиск до правильной. При нечитаемом авторе один путь принимал text-only.

**Правка.** `expected_author` и строгий флаг передаются прямо в общий finder; metadata finder-а используется до повторного broad DOM extraction; author missing в строгой проверке отклоняется.

**Почему критично.** Автор должен быть частью условия поиска, а не фильтром только для первого найденного текста.

### C13. Parallel-flow ждал `DOMContentLoaded` до начала открытия комментариев

**Симптом.** Browser уже показывал видео, но исполнитель десятки секунд не переходил к комментариям. В свежем production-логе между `main_browser_created` и `main_account_ready` были интервалы около 30–34 секунд. В read-only замере публичной страницы response commit наступил примерно на 0,7 с, `DOMContentLoaded` — на 1,1 с, а comment trigger появился позже, примерно на 5,3 с. Следовательно, ожидание одного события загрузки не гарантирует готовность кнопки и не должно блокировать активный DOM-probe.

**Причина.** Начальный `page.goto(..., wait_until="domcontentloaded")` полностью предшествовал login/comment probes. Кроме того, fast reply сначала выполнял стабильную pre-probe до 1,1 секунды и лишь затем делал первый click. Один вызов общего opener-а также мог исчерпать конечное число стратегий и вернуться раньше своего временного бюджета, если кнопка ещё не была создана React.

**Правка.** В parallel DOM-first переход возвращается на `wait_until="commit"`. Сразу после commit параллельно запускаются классификация login-state и bounded early opener. Early opener повторяет короткие scoped-проходы каждые ~150 мс до 6 секунд и нажимает кнопку при её появлении; main требует реальный comment input и сохраняет action-ready proof, reply лишь открывает поверхность, а наличие строк по-прежнему проверяется строгим list probe. DEAD/CAPTCHA/BLOCKED отменяет opener. Возвраты на целевое видео и post-enrichment переходы используют тот же ранний navigation gate. Fast reply заменил обязательное ожидание 1,1 с одним мгновенным снимком уже открытого списка.

**Почему безопасно.** Полная загрузка TikTok не отменяется и продолжается после commit. Все прежние captcha/login, URL и strict-list проверки остаются. Если trigger не появился за ранний бюджет, workflow не объявляет успех: дальше работает существующий обычный opener/retry. Непараллельный режим сохраняет `DOMContentLoaded` и прежнюю human-like задержку.

### C14. Full-order reply зависал на одном родителе с неотправленным черновиком

**Доказательство из логов 2026-08-26.** Для `task_1063_parallel_reply_v1...` родитель найден, exact-текст ответа подтверждён, strict gate видел стрелку как disabled, а optimistic finder возвращал `reply_send_candidate_not_found`. После финального recovery черновик оставался в composer, тот же physical parent снова находился и отбрасывался как `reply_parent_already_attempted_this_account`. Поэтому внешне софт возвращался к тому же комментарию и хуже находил остальные. Тот же ответ воспроизводил базовую отправочную ошибку и в reply-only (`task_1065...`), но full-order усиливал её большим списком родителей на одной странице.

**Правка.** Optimistic send теперь распознаёт label-less SVG-стрелку по той же геометрии справа от exact bonded reply input, которую уже использовал strict gate; аксессуары (emoji, mention, GIF, media) по-прежнему исключаются. После исчерпания send-only recovery черновик очищается. Неудавшийся parent удаляется только из очереди текущего аккаунта и остаётся доступен следующему аккаунту, поэтому не блокирует остальных родителей. Если очистка доказанно не удалась, закрывается только загрязнённая page-попытка без штрафа cookie/account health; следующий аккаунт получает чистую страницу. Fast reply-open переводится с 10-секундного hard timeout на 4 секунды и затем использует уже существующий scoped composer recovery. Повторная auth-проверка перед reply ограничена 1,5 секунды, а зависший captcha DOM probe — 1,25 секунды; положительные captcha/logout результаты по-прежнему немедленно завершают попытку и заменяют аккаунт.

**Почему точечно и безопасно.** Геометрический fallback работает только внутри composer, привязанного к exact parent anchor, и только при полном совпадении введённого текста. Глобальный main composer не рассматривается. Неуспешный send без клика не считается отправленным; после реального клика сохраняется прежняя политика пользователя: пустой/запоздалый ответ TikTok сам по себе не является отказом.

## Проверка исправлений

- Добавлены отрицательные тесты: `Post enabled` без submit не занимает main-слот; явный API-reject не занимает main-слот; main Post resolver отбрасывает reply scope.
- Добавлены direct-DOM тесты обычного ответа, click-timeout с уже полученным reject и рассинхронизации композера.
- Добавлены тесты семантики ZWJ, skin-tone и variation selector.
- Добавлены тесты замены idle browser context после смены proxy и запрета смены при занятой page.
- Добавлен тест scheme-less proxy credentials; поиск по runtime-коду не находит прежних `proxy[:30]`/`proxy[:50]`.
- Добавлены регрессии для строгого primary-author match, запрета совпадения через display-name/mention, отсутствия text-only fallback после author miss и всех трёх production-входов reply-поиска.
- Добавлены проверки безопасного username source и сохранения exact reply draft до send-only recovery.
- Добавлены регрессии раннего navigation gate: parallel использует `commit`, legacy — `DOMContentLoaded`; ранний opener повторяет попытки до позднего появления trigger, сохраняет main composer proof и не делает обязательную reply pre-wait.
- Синтаксис изменённых Python-файлов проверен через `py_compile`; `git diff --check` ошибок не показал.
- Основной связанный набор после текущих правок: **563 passed**. Отдельный сфокусированный повтор новых регрессий: **8 passed**.
- Для ускорения открытия комментариев отдельно прошло **12/12** связанных тестов; полный файл из 352 тестов дошёл примерно до 90% без ошибок и был остановлен по просьбе завершить быстрее.
- Для текущего дефекта full-order reply расширенный набор `reply/captcha/logged_out` прошёл **221/221**; отдельно проверены positive logout/captcha, bounded timeout, label-less send arrow, очистка черновика и переход к другим parent-кандидатам.

## Второстепенные ошибки и риски — не исправлял

### S1. `PublishedMain` смешивает confirmed и unconfirmed

Класс называется «реально опубликовано», но не хранит `submitted_unconfirmed` и его конкретную причину. Статус затем восстанавливается косвенно как `not network_confirmed and not local_confirmed`. Теряется доказательная база, а барьер 6×1 работает по длине списка.

**Что улучшит.** Добавить явные `confirmation_state`, `evidence_reason`, `request_seen`, `api_status`, `observer_state`. Нужна миграция сериализации и тестов, поэтому это не точечная критичная правка.

### S2. 6×1 считает unconfirmed достаточным для перехода между волнами

Это защищает от дублей, но production-журналы показывают обратную цену: main-счётчик выглядит полным, а reply workers позже не находят часть родителей и тратят почти весь общий timeout.

**Что улучшит.** До reply-фазы делать короткую observer-проверку только unconfirmed mains и разделять `attempted seats` от `visible parents`. Автоматический repost допустим лишь при доказанном `request_seen=False`; остальные остаются ручной/observer-неопределённостью.

### S3. `success` без `comment_id` не защищён контрактом

Сейчас известные producers возвращают `status="success"` вместе с ID. Но `_publish_all_variants_on_account` отдельно вычисляет `success=False`, затем всё равно ставит `local_confirmed=True` для любого `success_status`. Ошибка будущего producer-а бесшумно создаст PublishedMain без подтверждения.

**Что улучшит.** Валидировать инвариант в одном конструкторе/фабрике: `success => comment_id or explicit local evidence`.

### S4. Main input discovery слишком дорогой и повторяет селекторы

По журналам готовый comments surface иногда найден быстро, но цепочка resolver-ов всё равно занимает несколько секунд. Селекторы и scoring повторяются в `publish_action.py` и `dom_actions.py`, поэтому исправление TikTok DOM в одном месте легко расходится с другим.

**Что улучшит.** Один scoped resolver с коротким fast-path по уже маркированному editor и диагностируемым fallback-порядком.

### S5. Ограниченный DOM-скан не гарантирует отсутствие пропусков на очень больших видео

При известном счётчике больше 500 комментариев лимит составляет 64 scroll-step; при неизвестном — 48. Код корректно пишет `scroll_limit_reached`, а не ложно объявляет список исчерпанным, но на видео с тысячами комментариев это всё равно bounded best-effort, не полный обход.

**Что улучшит.** Индексировать ответы comment-list API по `cid + author + normalized text`, а DOM использовать только для открытия уже известного родителя. Просто бесконечно увеличивать scroll budget дорого и не гарантирует порядок из-за виртуализации/ранжирования TikTok.

### S6. В старых журналах встречается `Future exception was never retrieved: TargetClosedError`

Это указывает на не полностью drained async-задачу при закрытии browser/page. Последние найденные записи относятся к старому периоду; текущий код уже использует cancel/drain и callback, забирающий исключение detached task. Поэтому считать это активным critical-дефектом без нового воспроизведения нельзя.

**Что улучшит.** Централизованный lifecycle task-set: cancel → await gather(return_exceptions=True) до закрытия контекста.

### S7. Rotation lock не является общим lease для всех executor-задач

Строгий барьер 6×1 берёт Redis lock непосредственно перед ротацией и закрывает свой thread-local browser pool. Но обычный выбор main/reply аккаунта не исключает proxy, который в этот момент заблокирован другой задачей; это умеет только monitor selection. Кроме того, planned/failure rotations внутри task координируются в основном локальными set/counter.

**Риск.** Другая executor-задача может открыть browser на мобильном proxy возле момента чужой ротации и получить IP-change во время сессии.

**Что улучшит.** Ввести единый Redis lease state (`available / in_use / rotating`) и временный typed-result `proxy_busy`, который selection/retry умеет ждать без объявления «нет аккаунтов». Просто добавить фильтр сейчас опасно: существующий API выбора возвращает только account/None и превратит краткий lock в ложную нехватку аккаунтов.

### S8. Критический путь сосредоточен в очень больших модулях

`publish_action.py`, `user_schema.py` и `dom_actions.py` содержат много связанных стратегий и строкового JS. Локальная правка легко оставляет параллельную ветку без той же защиты — именно так main direct-DOM отстал от reply direct-DOM.

**Что улучшит.** Разделить outcome classifier, main/reply DOM adapters и orchestration. Рефакторинг проводить контрактными тестами, не одновременно с изменением поведения.

### S9. Старый шаблон с одним вариантом попадает в выбор, но отклоняется при подтверждении

В журнале 2026-08-25 это записано как traceback `Нужно минимум 3 варианта комментария в шаблоне`. Обновлённый контракт заказа требует три варианта, а legacy-шаблоны с одним `main_comment` всё ещё показываются в списке. Ошибка обработана и бот продолжает работу, поэтому это не авария исполнения TikTok, но пользователь узнаёт о несовместимости слишком поздно.

**Что улучшит.** Помечать legacy-шаблон прямо в списке и по подтверждению вести в существующий мастер ввода трёх вариантов, а не в общий экран ошибки. Отдельно понизить ожидаемую бизнес-валидацию с `ERROR + traceback` до `WARNING`.

### S10. Полная runtime-сводка остаётся линейной по всему пулу аккаунтов

После устранения повторных cookie-разборов живой замер на 3205 аккаунтах занимает около 2,8 секунды вместо десятков секунд и больше не блокирует остальные API-запросы. Но endpoint всё ещё пересчитывает весь пул при каждом cache miss, поэтому дальнейший рост базы снова увеличит задержку админского экрана.

**Что улучшит.** Короткий server-side snapshot cache с явной инвалидацией после изменения аккаунта/proxy или фоновая агрегация. Это уже оптимизация админской диагностики, а не критичная правка отправки.

### S11. Несколько legacy selector engines могут расходиться

Активный путь использует scoped resolvers из `dom_actions.py`/`publish_action.py`, но рядом остаются `tiktok_selectors.py`, `reply_finder.py` и старые helpers с более широкими `div[contenteditable=true]`/`a[href*="/@"]`. Сейчас production flow проходит через безопасный путь, однако будущий caller может случайно вернуть legacy-поведение.

**Что улучшит.** Оставить один публичный API для main input, reply triple, Post и parent row; legacy adapters пометить deprecated и покрыть тестом импорта/caller map.

### S12. Повторный scroll при открытии reply-box выбирает container эвристически

Первый parent anchor уже видим, поэтому в текущем потоке это обычно не мешает. Но retry-ветка `open_reply_box` может выбрать визуальный `CommentListContainer`, который на текущем layout не является реальным scroll node.

**Что улучшит.** Переиспользовать общий ancestor resolver, который уже проверяет `scrollHeight > clientHeight` и computed `overflowY`.

### S13. Раннее открытие имеет защитный потолок 6 секунд

На очень медленном proxy React может создать comment trigger позже. Это больше не оставляет browser бесконтрольно ждать `DOMContentLoaded`: после раннего окна стандартные loading-aware и publish/reply open-retry продолжают работу. Но панель в таком случае не будет открыта в самый первый возможный миллисекундный момент.

**Что улучшит.** Адаптировать early-open deadline к наблюдаемому прогрессу DOM: продлевать окно, пока меняются ready-state/action markers, и завершать быстро при отсутствии любого прогресса или доказанном network/proxy failure.

### S14. Один и тот же reply-текст с доменом деградировал заметно чаще остальных вариантов

В приложенных логах вариант `ropof.cfd is the one...` последовательно получал disabled/no-candidate на нескольких аккаунтах и в full-order, и в reply-only, тогда как соседние варианты чаще отправлялись. Исправленная рассинхронизация selector-ов объясняет `candidate_not_found`, но нельзя исключить отдельную TikTok content/spam-политику для доменоподобного текста.

**Что улучшит.** Считать отдельно `exact text + send control hard-disabled` по hash текста и layout, не объявляя аккаунт плохим. Если после selector-правки один hash остаётся аномальным на разных аккаунтах, помечать текст как вероятно ограниченный TikTok и показывать оператору, а не бесконечно менять аккаунты.

## Идеи и альтернативные подходы — не внедрял

### I1. Evidence-state machine вместо строковых reason

Формировать единый outcome из независимых фактов: `post_ready`, `click_dispatched`, `request_seen`, `response_seen`, `api_accepted`, `comment_id`, `composer_transition`, `author_dom_seen`, `observer_seen`, `definitive_reject`. Затем одна таблица решает `confirmed / unconfirmed / retryable / terminal`. Это устранит несовпадения между main, reply, direct-DOM и HTTP-first.

### I2. Observer quorum перед reply barrier

Для confirmed-ID достаточно одного observer lookup по ID. Для unconfirmed — 2 независимых наблюдения или один author+exact-text match. Ненайденный комментарий не удалять из истории попыток, но не передавать reply worker-ам как существующего родителя.

### I3. Request fingerprint

При перехвате publish сохранять безопасный fingerprint из media ID, normalized text hash, account ID и timestamp window. Ответ сопоставлять с конкретным request, а не только с endpoint. В лог писать hash, не текст/credentials.

### I4. Replay-тесты на обезличенных DOM fixtures

Сохранять минимальные sanitized HTML-фрагменты композера в состояниях: main/reply, enabled/disabled, duplicate stale nodes, пустой DOM при непустой React-модели. Прогонять JS probes в браузерном contract-test — Python mocks не проверяют реальную семантику CSS selectors.

### I5. Адаптивные бюджеты по прогрессу, а не только по числу кандидатов

Продлевать main/reply search, если scrollTop меняется и появляются новые уникальные комментарии; останавливать раньше при нескольких scans без DOM-прогресса. Это лучше фиксированных 22/42 секунд на разных размерах видео.

### I6. Метрики качества main-фазы

Отдельно считать: `api_confirmed`, `author_local_confirmed`, `submitted_unconfirmed`, `definitive_reject`, `no_request_desync`, `observer_visible`, время input resolution и долю unconfirmed, найденных observer-ом. Без этого ускорение легко достигается ценой ложного success.

### I7. Stale-while-revalidate для тяжёлых админских сводок

Возвращать последний готовый runtime snapshot мгновенно, а обновление запускать один раз в фоне с защитой от параллельных одинаковых расчётов. В ответе показывать `generated_at`/возраст snapshot, чтобы скорость не маскировала устаревшие данные.

### I8. Network comment index вместо длинного DOM-scroll

Перехватывать уже выполняемые TikTok comment-list ответы, сохранять только нужные поля (`cid`, `parent`, `uniqueId`, normalized-text hash) в рамках текущего задания и находить main детерминированно. Перед кликом всё равно перепроверять mounted DOM row по CID/author+text.

### I9. Версионируемый selector contract

Для каждого resolver-а хранить ordered selectors, обязательные отрицательные признаки и telemetry: какой selector сработал, tag/role/data-e2e, main/reply scope, время. При смене DOM отчёт сразу покажет деградацию fast-path до broad fallback.

### I10. Composer state machine

Явные состояния `located → focused → exact_text → post_enabled → click_dispatched → request_seen → response/ambiguous`. Cleanup разрешать только терминальному состоянию, а recovery — только состоянию до клика. Это уберёт конфликтующие cleanup/retry действия, подобные C11.

### I11. Event-driven comment trigger observer

Вместо polling каждые 150 мс можно после commit поставить короткоживущий `MutationObserver`, который замечает только scoped comment trigger и подаёт сигнал Python-коду. Клик всё равно должен выполнять текущий проверенный resolver: прямой автоматический click из observer-а может конфликтовать с React hydration и trusted-event требованиями. Подход уменьшит число DOM-evaluate на слабых машинах, но требует browser contract-test на нескольких TikTok layouts.

### I12. Failure snapshot только для bonded reply composer

При `post_button_stayed_disabled` сохранять обезличенную диагностическую структуру: input/post rectangles, tag/role/data-e2e, disabled/aria-disabled, opacity, pointer-events, число accessory/send candidates и факт remount. Не сохранять текст ответа, cookies или HTML всей страницы. Такой snapshot быстро отделит смену TikTok layout от content-level запрета и не потребует гадать по одному reason.

## Что сознательно не менялось

- Не отключал `submitted_unconfirmed` целиком: при реально ушедшем request это создаст дубли.
- Не менял число аккаунтов, сам алгоритм/частоту ротации IP, задержки публикации и общие timeout-ы.
- Не увеличивал текущие reply timeout/scroll budget; закрепил уже действующий deep-budget при неизвестном счётчике тестом.
- Не делал косметический рефакторинг больших модулей.
- Не публиковал тестовые комментарии в реальный TikTok.

## Проверенный lifecycle browser/page — критичной правки не потребовал

- При отмене parallel main tasks корутины сначала `cancel`/`gather`, и только затем закрывается pool.
- `_try_main_account` закрывает page в `finally`, включая timeout/cancellation.
- `close_pool_page` не закрывает общий context, пока в нём остаётся другая занятая page; после последней page закрывает context, browser и локальный SOCKS lease.
- В строгом 6×1 порядок: завершить активные задачи → закрыть thread-local pool → вызвать rotation → открыть следующую волну. Ротация не начинается поверх живых страниц этой задачи.
