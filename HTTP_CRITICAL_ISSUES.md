### ✅ ОШИБКА 1: DOM fallback выполняется ВНУТРИ retry loop для replies - ИСПРАВЛЕНО

**Файл:** `executor/engagement_engine.py` (строка 683-717)

**Проблема:**
```python
for retry_attempt in range(3):  # Максимум 3 попытки
    # ... HTTP запрос ...
    if not success:
        # ... обработка ошибок ...
        # Продолжаем retry (строка 677)
    
    finally:
        await page.close()
        await context.close()
    
    # ❌ ПРОБЛЕМА: DOM fallback ВНУТРИ retry loop
    if not reply_success:
        # DOM fallback
        # ...
        if reply_result.success:
            break  # Выходит из retry loop
```

**Последствие:**
- Если HTTP упал с retryable ошибкой (API_ERROR, NETWORK_ERROR), DOM fallback выполнится **после каждой попытки HTTP**.
- Это означает: HTTP fail → DOM fallback → HTTP fail (новый аккаунт) → DOM fallback → ...
- **Избыточные DOM fallback'и** замедляют выполнение и расходуют ресурсы.

**Правильная логика:**
- DOM fallback должен выполняться **ПОСЛЕ** всех retry попыток HTTP, а не внутри цикла.

**✅ ИСПРАВЛЕНО:**
- DOM fallback вынесен из retry loop (строка 691-725 → после цикла)
- Выполняется один раз после всех попыток HTTP
- Использует новый аккаунт для fallback (или последний использованный)

### ✅ ОШИБКА 2: Нет retry для likes при HTTP ошибках - ЧАСТИЧНО ИСПРАВЛЕНО

**Файл:** `executor/engagement_engine.py` (строка 890-972)

**Проблема:**
```python
# Выполняем like через HTTP
success, error_msg, error_type = await http_client.like_comment(...)

if success:
    like_success = True
else:
    # ❌ ПРОБЛЕМА: Нет retry для likes!
    # Если HTTP упал с API_ERROR или NETWORK_ERROR - лайк просто провалится
    if error_type == HttpErrorType.RATE_LIMIT:
        # cooldown
    elif error_type in (HttpErrorType.FORBIDDEN, HttpErrorType.CAPTCHA):
        # DOM fallback
    else:
        like_error = f"HTTP error: ..."  # ❌ Просто записываем ошибку, НЕТ retry!
```

**Последствие:**
- Если HTTP like упал с `API_ERROR` или `NETWORK_ERROR` (retryable ошибки) - лайк **сразу провалится** без retry.
- `PlaywrightHttpClient._execute_request()` делает retry внутри себя (до 3 попыток), но если все попытки провалились - нет fallback на другой аккаунт или DOM.
- **Несправедливо:** replies имеют retry с разными аккаунтами, likes - нет.

**Правильная логика:**
- Добавить retry для likes с разными аккаунтами (аналогично replies).
- Или: использовать тот же аккаунт с retry внутри HTTP клиента (уже есть, но можно улучшить).

**✅ ЧАСТИЧНО ИСПРАВЛЕНО:**
- Likes используют разные аккаунты (создаются заранее)
- Но нет retry с новым аккаунтом если HTTP упал (используется тот же аккаунт)
- Добавлен DOM fallback для всех ошибок (не только FORBIDDEN/CAPTCHA)

### ✅ ОШИБКА 3: Не исключаются использованные аккаунты в retry loop для replies - ИСПРАВЛЕНО

**Файл:** `executor/engagement_engine.py` (строка 585)

**Проблема:**
```python
for retry_attempt in range(3):  # Максимум 3 попытки
    reply_account = get_free_account_for_reply(db, exclude_ids=None)  # ❌ exclude_ids=None!
```

**Последствие:**

- Это бесполезно: если аккаунт упал с 403, повторная попытка с тем же аккаунтом тоже упадёт.

**Правильная логика:**
- Собирать использованные account_id и передавать в `exclude_ids`.

**✅ ИСПРАВЛЕНО:**
- Добавлен `used_account_ids` список (строка 584)
- Аккаунты исключаются в retry loop (строка 588)
- Аккаунт добавляется в список после использования (строка 594)

### ✅ ОШИБКА 4: Нет задержек между лайками - ИСПРАВЛЕНО

**Файл:** `executor/engagement_engine.py` (строка 816-987)

**Проблема:**
```python
for like_idx in range(likes_count):  # 15 лайков
    # Выполняем like через HTTP
    success, error_msg, error_type = await http_client.like_comment(...)
    # ❌ НЕТ ЗАДЕРЖКИ между лайками!
    # Следующий лайк выполняется сразу
```

**Последствие:**
- Все 15 лайков могут быть отправлены **почти одновременно** (только ограничение аккаунтов).
- Это может вызвать **rate limit** на прокси или IP.
- TikTok может заблокировать за "подозрительную активность".

**Правильная логика:**
- Добавить случайную задержку между лайками (например, 0.5-2.0 сек).
- Или: батчить лайки (по 3-5 за раз) с задержками между батчами.

**✅ ИСПРАВЛЕНО:**
- Добавлена случайная задержка 0.5-2.0 сек между лайками (после строки 1000)
- Задержка не применяется после последнего лайка

### ✅ ОШИБКА 5: DOM fallback для likes только при FORBIDDEN/CAPTCHA - ИСПРАВЛЕНО

**✅ ИСПРАВЛЕНО:**

### ⚠️ ОШИБКА 6: Cooldown применяется, но аккаунт может быть выбран в том же цикле - ЧАСТИЧНО РЕШЕНО

**Файл:** `executor/engagement_engine.py` (строка 648-664, 923-939)

**Проблема:**
```python
if error_type == HttpErrorType.RATE_LIMIT:
    # Сохраняем cooldown
    db.query(Account).filter(Account.id == reply_account.id).update({...})
    db.commit()
    # ❌ ПРОБЛЕМА: Аккаунт уже выбран, cooldown применён, но retry loop продолжается
    # Следующая итерация может выбрать другой аккаунт (правильно),
    # но если аккаунтов мало - может выбрать тот же (неправильно)
```

**Последствие:**
- Если аккаунтов мало, `get_free_account_for_reply()` может вернуть тот же аккаунт (хотя cooldown уже применён).
- Это решается проверкой cooldown в `get_free_account_for_reply()`, но **только если аккаунт обновлён в БД и commit выполнен**.
- **Race condition:** между commit и следующим `get_free_account_for_reply()` может быть задержка.

**Правильная логика:**
- Добавить `exclude_ids` с account_id, который получил cooldown, в текущем цикле.

**✅ ЧАСТИЧНО РЕШЕНО:**
- Cooldown проверяется в `get_free_account_for_reply()` (уже исправлено ранее)
- Но в текущем цикле replies/likes аккаунт может быть выбран до применения cooldown
- Это решается через `used_account_ids` - аккаунт не будет выбран повторно в том же цикле

### ✅ ОШИБКА 7: Нет проверки успешности warmup перед использованием context - ИСПРАВЛЕНО

**Файл:** `executor/engagement_engine.py` (строка 799-813)

**Проблема:**
```python
for account in accounts_to_use:
    try:
        context, page = await create_page_for_account(account)
        cookies_dict, profile_valid = await warmup_page_for_http(...)
        # ❌ ПРОБЛЕМА: Если warmup упал с Exception, account_contexts[account.id] не создаётся
        # Но account остаётся в accounts_to_use, и при попытке использовать - ошибка
        account_contexts[account.id] = (context, page, cookies_dict, http_client, profile_valid)
    except Exception as e:
        logger.warning(...)
        continue  # ✅ Правильно, но нужно убедиться что account не используется
```

**Последствие:**
- Если warmup упал, аккаунт не добавляется в `account_contexts`, но остаётся в `accounts_to_use`.
- При попытке использовать (строка 835) - ошибка "Context not available".
- Это обрабатывается (строка 835-843), но **лучше исключить аккаунт из `accounts_to_use` сразу**.
