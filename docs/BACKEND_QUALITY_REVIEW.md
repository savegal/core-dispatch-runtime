# Повторная проверка backend — 7 ноября 2026

Проверена текущая рабочая версия, включая изменения предыдущего аудита. Основной фокус этой проверки — границы между SQL-транзакциями, отменой задач, HTTP-публикацией, выбором аккаунтов и независимым подтверждением видимости. Новых отправок комментариев в TikTok в этой проверке не было.

## Подтверждённые ошибки и исправления

### Повторная отмена оставляла работающий SQL-поток без владельца

Первый `cancel()` перехватывался, но следующий прерывал уже незащищённое ожидание `to_thread`. Сам поток при этом продолжал работу. Владелец мог закрыть SQLAlchemy Session до завершения записи или выйти раньше позднего резервирования аккаунта.

Добавлен общий `await_owned`: он защищает дочернюю операцию при каждом повторном запросе отмены, забирает её результат или ошибку и только после завершения передаёт отмену вызывающей стороне. Используется для SQL-операций quantity-движка, журнала HTTP-публикаций и контрольных точек видимости. Ошибка потока после отмены больше не превращает остановку в обычное завершение с ошибкой выбора аккаунта.

Тесты блокируют работающий поток, отменяют владельца трижды и проверяют, что тот остаётся владельцем до завершения работы. Отдельно проверены успешный и ошибочный результат потока, поздняя аренда аккаунта и запись принятого CID во время отмены финализации журнала.

### Остановка заказа не перепроверялась при резервировании слота

Первичная проверка состояния происходила до асинхронного резервирования. Изменение состояния заказа другой SQL-сессией между этими действиями не препятствовало резервированию.

`claim_action` проверяет актуальную запись Task после получения блокировки строки, включая `stopped`, `stopped_by_user` и `cancelled_by_user`. Уже остановленный заказ не расходует лимит отправок.

Сам планировщик также проверяет SQL-состояние на каждом проходе. При недоступном или запаздывающем сигнале Redis он завершает остановленный заказ, вместо повторного обхода заблокированных слотов до истечения времени.

### Медленный выбор аккаунта возвращал устаревшее разрешение на публикацию

Пока выбирался аккаунт, другая сессия могла остановить заказ, сменить владельца слота или изменить CID родительского комментария. После возврата селектора эти условия повторно не проверялись.

Добавлена отдельная проверка перед запуском публикации: актуальное состояние заказа, токен и состояние слота, а для ответа — принадлежность, видимость и точный CID родителя. Устаревший выбор не запускает публикацию; зарезервированный аккаунт освобождается. Проверка завершается SQL-коммитом до браузерных операций.

Возврат неиспользованной попытки защищён токеном и очищает этот токен. Повторная очистка или последующий `finally` не уменьшают счётчик прошлых отправок второй раз.

### Запоздавший результат публикации мог затереть новый слот

Финализация записывала состояние и CID без проверки актуального владельца. Старый результат мог затереть новый токен/CID или понизить уже подтверждённое состояние `visible` до `accepted`.

Финализация проверяет владельца и использует условный SQL UPDATE с task ID, токеном, исходным состоянием, CID и счётчиком отправок. Состояния `visible` и `absent`, полученные независимой проверкой, сохраняются. Освобождение собственной аренды аккаунта выполняется независимо от результата обновления слота.

### Проверка старого CID могла подтвердить уже заменённую публикацию

Проверка сохраняла снимок CID, ожидала сетевой ответ, затем безусловно меняла состояние слота. Если за это время слот получал другой CID, положительный результат старой проверки подтверждал новый CID без фактического наблюдения.

Теперь обновление привязано к исходным task ID, токену, CID и состоянию `accepted`. Истинное наблюдение старого CID сохраняется в его журнале, но не подтверждает новую публикацию. Первичная выборка также ограничена текущим заказом: переданные идентификаторы другого заказа не запускают чтение его публикаций.

### Новый заказ наследовал служебные флаги остановки

Общая очистка входящих настроек удаляла результаты выполнения, но сохраняла `stopped_by_user`, `cancelled_by_user`, `cancelled_at`, `cancel_reason` и `force_close_browsers`. API принимал их при создании новой задачи. Эти поля теперь исключаются из конфигурации заказа вместе с остальными служебными данными. Два теста через реальный обработчик API проверяют, что созданный заказ не наследует остановку и может зарезервировать первый слот.

## Проверка

До исправления первые 14 новых сценариев воспроизводили ошибки. Дополнительные три сценария воспроизвели запуск публикации после устаревшего выбора аккаунта; ещё два — сохранение флагов остановки в новом заказе; ещё один — продолжение обхода остановленного заказа без сигнала Redis. Добавлено 23 сценария, включая проверки идемпотентной очистки и финализации журнала.

Финальный полный unit-прогон на окончательном коде: **3102 passed**, 13 предупреждений pytest, 501,31 с. Профильный набор новых проверок и API-создания заказов: **35 passed**, 19,65 с. Браузерный HTTP-набор: **55 passed**, 316,92 с. Наборы пересекаются по проверяемым функциям; профильные тесты входят в общий unit-набор.

Полный unit-прогон перезапускался после обнаружения и исправления дополнительных ошибок, чтобы итоговый результат относился к окончательной версии кода. Промежуточные прерванные прогоны в эти результаты не включены.

В общий unit-прогон входят существующие проверки создания и повторов всех видов заказов, keyword-поиска и независимой видимости, баланса и возвратов, выбора и импорта аккаунтов, residential/mobile-маршрутов и аренды прокси, ограничений времени и трафика, авторизации API и отчётов. Они выполняются на тестовых данных и подменённых внешних сервисах.

55 транспортных сценариев используют настоящий Chromium и локальные HTTP-ответы: браузерные cookies, CSRF и SDK-заголовки, готовность подписывающего окружения, HTTP-поиск родителя, публикация main/reply через fetch, неопределённый ответ без повторной отправки, зависшее тело ответа, отмена после POST, журнал и контрольная точка. Наличие SDK в этих тестах не означает проверку настоящей подписи TikTok: его внешняя среда и ответы воспроизводятся локально.

Дополнительно успешно выполнены компиляция Python-модулей backend/bot, Ruff для неопределённых имён и `git diff --check`.

## Изменённые файлы именно этой проверки

## Границы выводов

Эти проверки подтверждают поведение кода на изолированной SQLite и локально обслуживаемых HTTP-ответах в настоящем Chromium. Это не подтверждение публичной публикации на живом TikTok, текущей конверсии аккаунтов или работоспособности платного прокси. PostgreSQL в этом окружении не запускался. Завершение процесса ОС не равнозначно корректной отмене корутины; восстановление после аварийного выхода по-прежнему опирается на SQL-журнал и сроки аренды.

Рабочие сервисы не перезапускались; Git commit и push в рамках этой проверки не выполнялись.
