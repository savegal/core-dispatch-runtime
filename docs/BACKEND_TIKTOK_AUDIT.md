# Backend и реальные проверки TikTok — 6 ноября 2026

Этот документ дополняет `QUANTITY_ORDER_REDESIGN.md`. Здесь перечислены изменения текущей проверки, а не весь накопленный diff проекта. Старые незакоммиченные изменения сохранены.

## Исправленные ошибки

1. **Неопределённая отправка не становится разрешением повторить POST.** Если публикационный helper прерван после входа в отправку, но квитанция ещё не сохранена, слот остаётся `uncertain`. Состояние `not_sent` разрешено только при доказанном отсутствии отправки. Полученный CID и запись журнала сохраняются даже при последующем исключении во время очистки cookies.
2. **Lease аккаунта освобождается при ошибке подготовки в БД.** Коммит выбранного аккаунта теперь находится внутри `try/finally`; сбой после резервирования больше не оставляет аккаунт занятым до истечения lease.
3. **Бюджет времени ограничивает сетевые ожидания.** `max_seconds` охватывает разрешение ссылки, подготовку браузера, отправки и проверки. Остановка пользователя прерывает принадлежащую заказу операцию, затем дожидается её очистки и фиксации квитанций. Внутренний `TimeoutError` не подменяется исчерпанием бюджета, если общий дедлайн ещё не истёк.
4. **Ошибка одной ветки чтения не теряет уже найденные CID.** Сохраняются положительные результаты и законченные проверки предыдущих веток; затем берётся следующий независимый читатель. Неполный/упавший запрос не доказывает отсутствие комментария. Отмена операции продолжает распространяться.
5. **Ответ защищён от устаревшего родителя.** Перед резервированием аккаунта проверяются заказ, URL, тип, публичное состояние главного комментария и совпадение сохранённого CID. Ответ не превращается в главный комментарий при потере родительского слота и не отправляется на заменённый CID.
6. **Passport использует TLS-профиль установленного поколения Chromium.** Выбирается поддерживаемый desktop-профиль curl_cffi не новее фактического браузера. В этой среде Chromium 145 и curl_cffi 0.17.0 поддерживают `chrome145`; прежний хардкод `chrome131` убран. Это согласование профиля, а не обещание прохождения антибот-проверок.
7. **HTTP 407 относится к прокси.** Ответ либо исключение CONNECT 407 возвращает недостоверную проверку с категорией `proxy_route`, `definitive=False`, `request_attempted=False`. Нет повторной попытки через тот же отвергнутый прокси другим HTTP-клиентом. Это не основание объявлять TikTok-сессию истёкшей. IP-проба также сообщает отдельную причину `proxy_authentication_required`.
8. **Диагностика маршрутов стала предметной.** `/accounts/pool_diagnostics` возвращает `route_policy`: отсутствующие/неверные/неактивные маршруты, sticky-сессии, мобильные маршруты без URL ротации, повторные назначения фиксированных резидентских маршрутов. Сводка не содержит адресов, логинов, паролей и не выполняет сетевые запросы. В списке аккаунтов credentials прокси полностью маскируются.
9. **Фоновая перепроверка завершает свой Playwright.** Каждое задание запускается через `asyncio.run`, поэтому перед закрытием его event loop выполняется `close_browser_pool(stop_playwright=True)`. Thread-local драйвер больше не сохраняется с привязкой к уже закрытому loop для следующего задания в том же потоке.

Ошибки управления исполнением и три режима устаревшего родителя воспроизведены регрессионными тестами. Исходные пять сценариев управления исполнением падали до исправления. Дополнительно проверены выбор TLS-профиля, классификация 407, маскировка данных и сводка маршрутов.

## Что подтверждено реальным TikTok

Использована разрешённая пользователем ссылка `https://vt.tiktok.com/ZSpNmy187/`. Прямое соединение включалось только в отдельных тестовых Python-процессах; `.env` приложения и сохранённые proxy аккаунтов не переписывались. Лимит 30 запусков не исчерпан.

- Короткая ссылка вернула HTTP 200 и разрешилась в media ID `7702187139005418774`. Сам по себе HTTP 200 страницы не доказывает доступность API или авторизацию.
- Отдельные строгие Passport-проверки трёх аккаунтов дали `valid=True`, `definitive=True`.
- Полная подготовка двух сессий через рабочие функции проекта прошла Passport, проверку входа и HTTP warmup. Ранние запросы списка комментариев не дали достоверного payload; эти ответы не были истолкованы как «комментариев нет».
- Последующий инструментированный запуск получил корректный `/api/comment/list/`: HTTP 200, JSON с одним комментарием, подпись подтверждена событием реального браузерного запроса. Первый ответ был пустым, штатная повторная попытка с обновлением `msToken` завершилась успешно. Независимый свежий запрос `cache=no-store` затем тоже вернул один комментарий с первой попытки. Значения cookies и подписей не выгружались в отчёт.
- Минимальная проверка отправки использовала настоящие функции подготовки и публикации. TikTok предъявил `captcha_challenge:verify` **до POST**. Отправка главного комментария не состоялась, ответ вслед за ним не запускался. В тестовом заказе №1248 сохранено `not_sent`, `dispatches=0`; в SQL-журнале ноль отправленных POST и ноль принятых публикаций. Финальный статус тестового заказа — ошибка CAPTCHA, а не успешное выполнение.
- Один ранний запуск чтения не имеет сохранённого результата инструмента и не используется как доказательство успеха. При последующих запусках этапы сохранялись в отдельные обезличенные JSON-файлы.
- Дополнительный прямой GET ссылки на комментарий из пользовательской выгрузки дал HTTP 200 после одного перенаправления. Конечный URL сохранил media ID и тот же параметр `cid`. Это проверка маршрута ссылки; тонкий HTML-ответ 1462 байта не доказывает публичную видимость комментария.

**Успешная реальная публикация, независимая публичная видимость новой публикации, реальная конверсия 10–18% и работа через будущего резидентского провайдера в этой сессии не подтверждены.** Локальные Chromium-тесты проверяют полный путь POST, родителя ответа, счётчики, журнал и восстановление на управляемых HTTP-ответах.

## Текущее состояние настроенного пула

На момент первоначальной проверки: 3026 активных аккаунтов, один активный фиксированный резидентский маршрут, все активные аккаунты назначены на него. В этом маршруте нет sticky-шаблона, он не мобильный и не имеет URL ротации. Реальная IP-проба вернула HTTP 407.

Это не соответствует выбранной модели «отдельный IP на аккаунт»: нужны отдельные рабочие маршруты либо провайдерский sticky-шаблон и проверка фактических выходных IP. Код не придумывает уникальные IP и не заменяет неработающий прокси прямым подключением. Статический статус `active` в таблице прокси не является доказательством сетевой готовности.

Предпочтение регионов FR/ES/GB/DE/IT/PL/NL/US сохранено как приоритет при сопоставимом состоянии аккаунтов. В первоначальном срезе активного пула известны CA/UA, у большинства регион неизвестен. Регион cookies не подменялся желаемой страной. Предпочтение региона не означает гарантированной конверсии.
