# HTTP-исполнение и учёт трафика — 7 ноября 2026

Продолжение разработки после повторного аудита backend. Изменения относятся к существующему веб-транспорту. Мобильный API по предположениям о скриншотах стороннего сервиса не добавлялся.

## Подтверждённые проблемы

1. Отмена `TrafficMeter.flush()` могла завершить корутину раньше SQL-потока. При ошибке такого потока измеренный пакет терялся; при успешной записи владелец не дожидался фактического коммита. Закрытие счётчика также позволяло отмене прервать ещё незавершённое измерение `request.sizes()`.
2. `QuantityResult.to_dict()` обращался к сохранённым ORM-объектам. После `expire_all()` он делал новые SELECT, после закрытия такой сессии получал `DetachedInstanceError`, а при изменении объектов мог смешать старые подтверждения с новым состоянием слотов.
3. Проверка бюджета происходила после первоначального разрешения URL и части проверок видимости. Даже уже исчерпанный лимит не останавливал эти первоначальные HTTP-чтения. После долгого выбора аккаунта бюджет также не перепроверялся перед публикацией.
4. Проверка видимости могла переходить к следующему читателю или ветке после того, как предыдущая уже исчерпала бюджет.
5. Счётчик сохранял измеренные байты пачкой с задержкой. Проверка только SQL не учитывала ещё не записанные измерения того же процесса.
6. Остановка в SQL проверялась между этапами планировщика, но ожидание уже зависшего HTTP-этапа зависело от внешнего callback остановки. При отсутствующем сигнале Redis оно могло продолжаться до общего тайм-аута.

Первый набор воспроизвёл 10 падающих сценариев. Дополнительные проверки воспроизвели расход бюджета после выбора аккаунта, переход к следующему читателю/ветке и навигацию при уже измеренном, но ещё не сохранённом трафике.

## Что изменено

- Запись трафика принадлежит вызывающей операции до завершения потока даже при повторной отмене. Успешно записанный пакет не возвращается в буфер; пакет с ошибкой восстанавливается. Параллельные закрытия используют одну операцию ожидания измерений и записи; повторное закрытие может повторить неудавшуюся запись.
- Активные счётчики доступны через слабые ссылки, привязанные к engine и event loop. Перед проверками бюджета сохраняются уже измеренные байты текущего заказа. Код не ожидает счётчики другого event loop/потока. Слабые ссылки не удерживают браузерные контексты.
- При заданном бюджете ошибка сохранения измерений останавливает новые запросы с причиной `quantity_traffic_accounting_unavailable`. Буфер сохраняется для повторной записи; добавлено понятное пользователю объяснение. Без заданного бюджета сбой вспомогательного счётчика сам по себе не становится запретом выполнения.
- Остановка и бюджет проверяются до первоначальной навигации, перед live-проверкой видимости, после выбора аккаунта и при переходах между читателями/ветками. Ранее полученное положительное свидетельство видимости сохраняется, даже если бюджет не позволяет читать следующую ветку.
- Во время выполнения quantity-заказа отдельная короткая SQL-сессия проверяет остановку и бюджет примерно раз в секунду. Она не разделяет ORM-сессию с HTTP-операцией. При остановке активная операция отменяется и проходит существующую процедуру сохранения квитанций и освобождения ресурсов.
- Снимок результата содержит обычные данные слотов, настроек и прежних результатов лайков. Его сериализация не обращается к SQL и не зависит от дальнейшего изменения/закрытия исходной сессии. Повторный `to_dict()` возвращает независимые копии вложенных данных.

## Проверка

Добавлено 19 unit-сценариев: повторная отмена, успешный и ошибочный SQL-коммит, закрытие при незавершённом измерении, повторное и параллельное закрытие, независимость снимка от ORM-сессии, бюджет до навигации/публикации/чтения, остановка и бюджет во время зависшего этапа, несохранённые измерения и изоляция event loop.

Два новых интеграционных сценария используют настоящий Chromium и HTTP-сервер на localhost. Они проверяют передачу нативных размеров GET/POST в SQL и остановку следующей навигации после скачивания 1 МиБ с заданным лимитом 1 МиБ. Оба прошли.

Полный Chromium-прогон: **57 passed**, 294,21 с. Полный unit-прогон на окончательной версии: **3121 passed**, 13 предупреждений pytest, 544,89 с. Все 19 новых unit-сценариев входят в этот общий набор.

Профильные пересекающиеся наборы до финального прогона проходили: 85, 129 и 130 тестов. Окончательный новый unit-модуль: 19 passed. Компиляция Python, Ruff для изменённых модулей и проверка неопределённых имён проекта прошли.

## Границы точности

Бюджет относится к измеренным браузером байтам, а не к счёту провайдера прокси. Незавершённые запросы, TLS/туннельные расходы и задержка сохранения измерений других процессов допускают превышение порога. Система останавливает дальнейшую работу на контрольных границах; это не гарантия жёсткого сетевого лимита до последнего байта.

Проверки используют SQLite и локальный HTTP. Живые публикации TikTok, прохождение CAPTCHA, конверсия аккаунтов, реальный расход у провайдера и PostgreSQL этим прогоном не подтверждались. Рабочие процессы не перезапускались; Git commit/push не выполнялись.
