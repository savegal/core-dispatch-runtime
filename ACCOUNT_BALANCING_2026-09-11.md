# Балансировка аккаунтов и проверка сессий — 11.09.2026

Выбор главных комментариев и ответов переведён на общую сохраняемую очередь назначений. В пределах пригодного пула первым выбирается аккаунт, который дольше не получал назначений. После назначения он переходит в конец очереди независимо от результата публикации. Качество сессии служит дополнительным критерием при одинаковой давности назначения; высокий балл больше не позволяет одному аккаунту постоянно опережать остальные.

## Как работает очередь

- История назначения (`last_assigned_at`, `assignment_count`) хранится в БД и переживает перезапуск.
- Главные комментарии и ответы используют общую историю. Назначение на ответ тоже сдвигает аккаунт в конец очереди главных.
- При первом запуске новой версии используется существующий `last_used_at`; уже активно использованные аккаунты не получают преимущество перед давно не использованными.
- Назначение фиксируется до запуска браузера. Неудачная подготовка или отправка не оставляет аккаунт в начале очереди.
- Резервирование в БД атомарное: два исполнителя не могут одновременно получить один аккаунт для зарезервированного задания. Старое назначение проверяется при записи; устаревший кандидат пропускается.
- Резервирование ограничено сроком. После завершения оно снимается по токену владельца, после аварийного завершения истекает. Освобождение старого токена не снимает новое резервирование другого исполнителя.
- При достаточном пригодном пуле следующие заказы выбирают другие аккаунты. Если пригоден только один аккаунт или действуют ограничения пула/прокси, повторное использование остаётся возможным.
- В журнал добавлена запись `[ACCOUNT_ASSIGNMENT]` с аккаунтом, типом задания, числом назначений и политикой выбора.

Деление нагрузки на `MAX_ACTIONS_PER_ACCOUNT=999999` больше не управляет очередностью. Старый балл качества сохранён как вспомогательный критерий.

## Валидация

В HTTP-валидаторе неопределённые ошибки, HTTP 403 и общая строка `message=error` больше не считаются доказательством мёртвых cookies. Явный отказ авторизации отделён от отсутствия подтверждения. Ошибка проверки одного аккаунта не обрывает всю проверяемую группу. Пустое значение cookie не считается действующей сессией.

У служебного валидатора есть отдельный `last_validation_attempt_at`: проверяются сначала никогда не проверявшиеся, затем самые давно проверенные аккаунты. Мониторинг и отправки не вытесняют аккаунты из этой очереди изменениями `last_checked_at`. Сохраняются причины и время действующего runtime-кулдауна. Если во время HTTP-запроса аккаунту заменили cookies/прокси, изменили статус или выдали задание, устаревший результат не применяется.

Автоматический запуск этого фонового валидатора в исполнителе был отключён до изменения и не включался. Полная проверка этой задачи выполнена отдельной командой `tools/audit_account_pool.py --http --apply-valid --concurrency 5`. Отчёт сохранён в `scratch/account-pool-validation.json`; он содержит диагностические результаты без значений cookies, паролей и токенов.

## Скорость и проверка

На большой базе обнаружен повторный SQL ORDER BY по строкам с cookies для каждого небольшого блока. В SQLite теперь сначала один раз сортируются ID, затем загружаются нужные блоки. Прокси проверяется один раз за выбор, характеристики уже проверенного кандидата повторно не вычисляются без необходимости.

Контрольное профилирование обхода примерно 2500 записей на копии базы: 14,7 с до оптимизации SQL и 2,2 с после. Это замер конкретного выбора под профилировщиком, не обещание длительности каждого заказа.

Проверены два полных обхода пула из 45 аккаунтов с разными баллами качества: за 90 назначений каждый выбран ровно два раза. Также проверены последовательные и параллельные назначения, общая очередь main/reply, восстановление после истечения резервирования, защита от устаревшего токена, пустые cookies, миграция, валидация и существующие режимы прокси.

На отдельной копии пользовательской БД штатные селекторы выполнили 120 последовательных назначений, чередуя главные комментарии и ответы: **120 разных аккаунтов, ни одного повтора**. Результат сохранён в `scratch/account-balance-real-pool-test.json`. Эти назначения не попали в рабочую БД и не публиковали комментарии.

Финальный общий прогон: 99 тестов пройдено. Дополнительный прогон расширенного файла валидации: 12 пройдено, включая три новых проверки, отсутствовавшие в первоначальной коллекции общего прогона. Итого проверены 102 разных теста без ошибок. Повторное применение миграции ничего не меняет; `PRAGMA quick_check` рабочей БД вернул `ok`.

На момент завершения задачи исполнитель и API не запущены. Новая очередь будет использоваться при следующем запуске программы; миграция к текущей рабочей БД уже применена. Автоматические публикации для проверки этой правки не запускались.
